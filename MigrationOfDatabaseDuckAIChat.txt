`v-html` inserts the string as raw HTML. Do not use it with untrusted or user-provided content unless you sanitize it first, because unsanitized HTML can allow XSS attacks.

Also note that Vue will not compile Vue components or directives inside the string. For example, `<MyButton />` or `@click="..."` in the HTML string will not behave as Vue components or bindings.

In the previous script, this line:

```javascript
topics.createIndex(
  { title: 1 },
  { unique: true }
);
```

creates a **unique index on the `title` field of the `topics` collection**.

It does not mean `topics.title` is a field path inside each exercise. Here, `topics` is the collection name and `title` is a field in each Topic document.

For example, these documents would be valid:

```javascript
{ _id: ObjectId("..."), title: "Arrays" }
{ _id: ObjectId("..."), title: "Recursion" }
```

But this would fail:

```javascript
db.topics.insertOne({ title: "Arrays" });
```

if a document with `title: "Arrays"` already exists. MongoDB would return a duplicate-key error because the `title` value must be unique. A unique index enforces that uniqueness at the database level, not just in your application code. [1]

A normal index:

```javascript
db.topics.createIndex({ title: 1 });
```

mainly improves query performance:

```javascript
db.topics.findOne({ title: "Arrays" });
```

A unique index does both:

- improves lookup performance;
- prevents duplicate values.

You can inspect the indexes with:

```javascript
db.topics.getIndexes();
```

You should see something similar to:

```javascript
[
  {
    name: "_id_",
    key: { _id: 1 }
  },
  {
    name: "title_1",
    key: { title: 1 },
    unique: true
  }
]
```

The reason it is useful in your migration is that multiple exercises may have the same first topic:

```javascript
Exercise 1: topics: ["Arrays", "Loops"]
Exercise 2: topics: ["Arrays", "Functions"]
```

Both exercises should reference the same Topic document:

```javascript
{
  _id: ObjectId("abc123"),
  title: "Arrays"
}
```

The unique index guarantees that only one Topic document with `title: "Arrays"` can exist.

One important detail: create the unique index only after checking whether duplicate Topic documents already exist. If duplicates already exist, index creation will fail. You can find duplicates with:

```javascript
db.topics.aggregate([
  {
    $group: {
      _id: "$title",
      count: { $sum: 1 },
      ids: { $push: "$_id" }
    }
  },
  {
    $match: {
      count: { $gt: 1 }
    }
  }
]);
```

If topic titles should be case-insensitive—for example, `"Arrays"` and `"arrays"` should count as the same topic—you can create the index with a case-insensitive collation:

```javascript
db.topics.createIndex(
  { title: 1 },
  {
    unique: true,
    collation: {
      locale: "en",
      strength: 2
    }
  }
);
```

Then use the same collation when searching or upserting:

```javascript
db.topics.updateOne(
  { title: "arrays" },
  {
    $setOnInsert: {
      title: "arrays"
    }
  },
  {
    upsert: true,
    collation: {
      locale: "en",
      strength: 2
    }
  }
);
```

For your current migration, if `"Arrays"` and `"arrays"` should be treated as different topics, the simple index is sufficient:

```javascript
db.topics.createIndex({ title: 1 }, { unique: true });
```

Use `mongodump` to create a backup and `mongorestore` to restore it. These are command-line tools, so run them in your operating system’s terminal—not inside `mongosh`. MongoDB’s Database Tools package provides both commands. [1,2]

Assume:

- Database: `my_database`
- Connection: `mongodb://localhost:27017`
- Migration file: `migrate-exercises.js`

## 1. Create a backup

From a terminal:

```bash
mongodump \
  --uri="mongodb://localhost:27017/my_database" \
  --out="./backup-before-migration"
```

This creates a directory similar to:

```text
backup-before-migration/
└── my_database/
    ├── exercises.bson
    ├── exercises.metadata.json
    ├── topics.bson
    └── topics.metadata.json
```

For a MongoDB server requiring authentication:

```bash
mongodump \
  --uri="mongodb://username:password@localhost:27017/my_database?authSource=admin" \
  --out="./backup-before-migration"
```

If your password contains special characters, use a properly URL-encoded connection string or omit the password and let the tool prompt you.

For a replica set where writes may continue during the backup, you can use `--oplog` for a more consistent backup:

```bash
mongodump \
  --uri="mongodb://localhost:27017/my_database" \
  --oplog \
  --out="./backup-before-migration"
```

`--oplog` is intended for replica sets and must be paired with `--oplogReplay` during restoration. [1,2]

For a small local database where you can stop application writes during the backup, the first command is usually sufficient.

## 2. Run the migration script

Run the migration using `mongosh`:

```bash
mongosh \
  "mongodb://localhost:27017/my_database" \
  migrate-exercises.js
```

Or, if you are already inside `mongosh`:

```javascript
load("migrate-exercises.js");
```

If authentication is required:

```bash
mongosh \
  "mongodb://username:password@localhost:27017/my_database?authSource=admin" \
  migrate-exercises.js
```

Before running the migration against production, you can first restore the backup into a separate test database and run the script there.

## 3. Restore the backup if necessary

Stop the application or prevent writes first. Then restore the backup with `--drop`:

```bash
mongorestore \
  --uri="mongodb://localhost:27017/my_database" \
  --drop \
  "./backup-before-migration/my_database"
```

`--drop` drops each collection being restored before importing its backup. This is important because, without it, existing documents that have the same `_id` are not overwritten and can cause duplicate-key errors. It does not drop collections that are not present in the backup. [3]

With authentication:

```bash
mongorestore \
  --uri="mongodb://username:password@localhost:27017/my_database?authSource=admin" \
  --drop \
  "./backup-before-migration/my_database"
```

If you used `--oplog` during the backup:

```bash
mongorestore \
  --uri="mongodb://localhost:27017/my_database" \
  --drop \
  --oplogReplay \
  "./backup-before-migration/my_database"
```

## Recommended sequence

```bash
# 1. Back up the database
mongodump \
  --uri="mongodb://localhost:27017/my_database" \
  --out="./backup-before-migration"

# 2. Run the migration
mongosh \
  "mongodb://localhost:27017/my_database" \
  migrate-exercises.js

# 3. If the result is wrong, restore the backup
mongorestore \
  --uri="mongodb://localhost:27017/my_database" \
  --drop \
  "./backup-before-migration/my_database"
```

The `--drop` option is destructive for the collections included in the backup, so verify the database name and backup path carefully before executing the restore. Also, keep the backup directory until you have verified the migrated data.
